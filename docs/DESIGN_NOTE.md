## 1. Architecture & End-to-End Request Flow

```
[ User Browser / React Form ]
       │
       │  1. Submits question (e.g., "Which keyboard is below ₱2,000?")
       ▼
[ frontend/src/pages/AssistantPage.jsx ]
       │
       │  2. Calls api.askAssistant(question) via fetch
       ▼
[ Express Router: backend/src/routes/assistant.js ]
       │
       │  3. Rate limiting (20 req/min) & Zod validation (3-300 chars)
       │  4. Fetches active products (Prisma / PostgreSQL or memoryStore fallback)
       ▼
[ Catalog Retrieval & Ranking: backend/src/services/assistant.js -> rankProducts() ]
       │
       │  5. Filters: active === true, stock > 0, price <= parsed budget
       │  6. Ranks by keyword relevance against title, category, description
       │
       ├─── [ No Qualifying Candidates ] ──► Returns honest no-match response immediately
       │                                     (Provider is NOT called: avoids latency, cost & hallucinations)
       │
       └─── [ Qualifying Candidates Found ] (Top 3 candidates)
              │
              ▼
[ Server-Side AI Integration: backend/src/services/aiProvider.js -> generateAssistantDraft() ]
       │
       │  7. Sends strict prompt + public candidate subset to Google Gemini API
       │     Key kept server-side in backend/.env; passed via x-goog-api-key header (not URL)
       │     Configured with 5000ms AbortSignal timeout
       │
       ├─── [ Provider Failure / Timeout / 503 / Missing Key ]
       │      │
       │      └──► Falls back seamlessly to buildRuleBasedResponse()
       │
       └─── [ Valid Provider JSON Draft Returned ]
              │
              ▼
[ Server Grounding & Output Verification: backend/src/services/assistant.js ]
       │
       │  8. Intercepts draft.recommendedProductIds
       │  9. Rejects unknown/hallucinated IDs: filters strictly against server candidate set
       │ 10. Constructs recommendedProducts & sources directly from authoritative catalog records
       ▼
[ HTTP 200 Response: { answer, recommendedProducts, sources } ]
       ▼
[ frontend/src/pages/AssistantPage.jsx ]
          Renders natural answer, clickable product recommendation links (/products/:id),
          and verified authoritative source badges.
```

## 2. Core Design Decisions

### Decision 1: Which product fields go to the provider, and why are those fields enough?
* **Fields Sent:** `id`, `name`, `category`, `price`, `stock`, and `description`.
* **Rationale:** These public fields provide all factual context needed to evaluate features, category relevance, budget adherence, and physical availability. Internal operational details (e.g., `createdAt`, `updatedAt`, database primary keys of related tables, margin metrics, or supplier data) and sensitive customer information (names, emails, physical addresses, order histories) are strictly excluded. Prices are explicitly converted from database decimal objects to standard numeric values beforehand.

### Decision 2: How do you prevent a source id or recommended product from being invented?
* **Enforcement Strategy:** The LLM draft is treated strictly as untrusted text. The server maintains an in-memory Map of verified catalog candidates (`candidateMap = new Map(candidates.map(c => [c.id, c]))`).
* Any ID returned by the model in `recommendedProductIds` that is not present in `candidateMap` is discarded immediately.
* Furthermore, the actual `recommendedProducts` array and `sources` array returned to the frontend are **never generated by the model**. They are constructed exclusively by mapping the verified IDs back to authoritative database records. This guarantees 100% genuine IDs, valid routes (`/products/:id`), and exact prices.

### Decision 3: What happens when the catalog has no match? Should the provider be called?
* **Policy:** When catalog retrieval yields zero matching in-stock products (e.g. asking for "sneakers" or an item with stock 0), **the AI provider is not called**.
* **Rationale:** Calling an LLM when zero relevant catalog facts exist wastes API quota, introduces unnecessary network latency, and significantly increases the probability of conversational hallucinations. Instead, the server instantly returns an honest, deterministic response:
  ```json
  {
    "answer": "I could not find an in-stock product matching that request.",
    "recommendedProducts": [],
    "sources": []
  }
  ```

### Decision 4: What happens when the provider is unavailable? What can the existing rules still answer?
* **Policy:** If the Gemini API experiences high demand (HTTP 503), quota limits (HTTP 429), timeouts (>5000ms), network errors, or if `GEMINI_API_KEY` is omitted, the error is caught safely and logged without exposing secrets.
* The system seamlessly falls back to `buildRuleBasedResponse(candidates)`.
* **Fallback Capabilities:** The rule-based engine still parses Philippine Peso budgets (`parseBudget`), filters in-stock active items, ranks them by keyword score, and formats a grammatically correct recommendation referencing actual product names, formatted prices (`₱1,850`), and working links. The customer never experiences an uncaught server error or infinite loading spinner.

### Decision 5: If earlier labs added user accounts, which catalog data is public and where are permissions enforced?
* **Policy & Boundaries:** The product catalog (names, prices, descriptions, stock availability, categories) is public read-only information accessible without authentication.
* Sensitive operations (mutating products, managing inventory, accessing customer orders, user profiles, credentials) require authenticated JWT / session tokens and role-based permissions (Admin/Customer) enforced at the Express route middleware layer.
* The assistant route (`/api/assistant/questions`) only accesses public catalog query functions and never receives or forwards user authentication tokens or private records to any AI provider.

## 5. Team Reflection & Issue Resolved

* **Key Contribution:** Implemented resilient server-side retrieval, secret isolation via `x-goog-api-key` headers in `aiProvider.js`, and strict catalog ID verification preventing hallucinated products.
* **Challenge Encountered & Resolved:** During initial testing with Gemini REST models, upstream spikes in demand caused temporary HTTP 503 responses. If unhandled, this would cause client requests to hang or crash with an internal error. By wrapping the provider invocation in a defensive try/catch block with `AbortSignal.timeout(5000)` and designing `buildRuleBasedResponse()`, the system immediately provides accurate catalog recommendations and sources regardless of upstream AI provider stability.
